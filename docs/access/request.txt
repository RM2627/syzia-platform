==================================================
1. PRINCÍPIO DO NOVO MODELO
==================================================

A VIRELOQ NÃO terá cadastro administrativo público.

Ninguém deve conseguir entrar na plataforma, clicar em “Criar conta”
e criar livremente um usuário ou organização.

O provisionamento seguirá esta hierarquia:

SUPER ADMIN VIRELOQ
→ cria/ativa a empresa
→ cria/provisiona o primeiro Administrador da empresa

ADMINISTRADOR DA EMPRESA
→ cria/provisiona os usuários da própria organização

USUÁRIO
→ somente ativa um acesso que já foi previamente provisionado.

O usuário não escolhe livremente:
- organização;
- papel;
- permissões;
- trial;
- plano.

Esses dados já devem existir antes da ativação da conta.

==================================================
3. CÓDIGO DA EMPRESA
==================================================

Cada organização deve possuir um código de acesso empresarial próprio.

Esse código:
- identifica o tenant durante autenticação;
- NÃO é uma senha;
- NÃO concede acesso sozinho;
- deve ser diferente do organization_id interno;
- deve ser diferente do slug público sempre que apropriado;
- deve ser estável;
- deve ser fácil de informar ao funcionário;
- deve ser suficientemente distintivo para evitar colisões.

Exemplo conceitual:

MS Auto Details
Código VIRELOQ: MSA7K2

A geração deve ocorrer server-side.

Garantir unicidade no banco.

Não utilizar sequência previsível que exponha quantidade de empresas ou
informações internas desnecessárias.

==================================================
4. USERNAME
==================================================

Cada usuário deve possuir username operacional.

Padrão sugerido automaticamente:

nome.sobrenome

Exemplo:

Rodrigo Santos
→ rodrigo.santos

O username deve ser:
- normalizado;
- case-insensitive;
- validado;
- editável pelo administrador antes da criação;
- único DENTRO DA ORGANIZAÇÃO.

Não exigir unicidade global.

Deve ser permitido:

Empresa A + rodrigo.santos
Empresa B + rodrigo.santos

Mas NÃO:

Empresa A + rodrigo.santos
Empresa A + rodrigo.santos

A identidade operacional deve resolver de forma inequívoca:

organization + username → usuário autorizado.

Adicionar constraint/índice adequado no banco.

8.1. E-MAIL OBRIGATÓRIO DO ADMINISTRADOR
==================================================

Todo Administrador de empresa deve possuir um e-mail cadastrado.

Para o PRIMEIRO Administrador, provisionado pelo Super Admin, o e-mail é
OBRIGATÓRIO.

Para qualquer novo usuário que receba posteriormente o papel
Administrador, também deve existir e-mail válido cadastrado antes da
concessão desse papel.

O e-mail NÃO substitui o username como identidade operacional de login.

O login normal permanece:

Código da empresa
+
Username
+
Senha

O primeiro acesso permanece:

Código da empresa
+
Username
+
Código temporário
→ definição da senha definitiva.

Portanto, o primeiro acesso NÃO deve depender da entrega de um e-mail.

O e-mail do Administrador deverá ser utilizado como canal adicional para:
- comunicação administrativa;
- alertas importantes de segurança;
- notificações relevantes da VIRELOQ;
- recuperação de acesso, quando essa funcionalidade estiver disponível e
  devidamente configurada.

Quando uma funcionalidade depender da propriedade do endereço de e-mail,
exigir verificação adequada do endereço antes de confiar nele.

O Super Admin deve continuar possuindo mecanismo administrativo seguro
para redefinir o acesso de um Administrador caso a recuperação por e-mail
não esteja disponível.

Para usuários não administrativos:
- e-mail permanece opcional;
- telefone permanece opcional;
- username continua obrigatório.

Não voltar a transformar e-mail em requisito para criação ou primeiro
acesso de funcionários comuns.

==================================================
9. CÓDIGO TEMPORÁRIO
==================================================

O código temporário NÃO é a senha permanente.

Requisitos:

- gerado criptograficamente;
- aleatório;
- uso único;
- validade limitada;
- número limitado de tentativas;
- revogável;
- novo código invalida o anterior;
- não armazenar em texto puro recuperável no banco;
- não registrar o valor em logs;
- não enviar o valor para clientes não autorizados;
- não permitir reutilização depois da ativação.

Definir uma validade inicial adequada, preferencialmente configurável.
Sugestão inicial: 48 horas.

Documentar a decisão.

18. LOGOUT AUTOMÁTICO POR INATIVIDADE
==================================================

Implementar política de sessão por inatividade.

Valor inicial:

30 minutos de INATIVIDADE.

Não significa 30 minutos desde o login.

Interações legítimas do usuário reiniciam o contador.

Não considerar como atividade:
- polling;
- refresh automático;
- atualização de sessão;
- chamadas de background;
- eventos internos sem interação humana.

Antes do logout, mostrar aviso, por exemplo:

“Sua sessão está prestes a expirar.”

“Por segurança, você será desconectado em 60 segundos.”

[ Continuar conectado ]

Se não houver interação:

- encerrar sessão;
- limpar estado sensível;
- retornar para login;
- não deixar dados de outra pessoa acessíveis.

31. NÃO IMPLEMENTAR AUTENTICAÇÃO INSEGURA PARA CUMPRIR O PEDIDO
==================================================

Apresente no relatório:
- limitação técnica encontrada;
- alternativas seguras avaliadas;

- solução escolhida;

A interface não deve expor detalhes técnicos utilizados internamente para
adaptar o modelo ao provedor de Auth.

32. DESATIVAÇÃO DE USUÁRIO
==================================================

O Administrador da organização deve poder desativar usuários da própria
empresa conforme suas permissões.

Usuário desativado:
- não consegue realizar novo login;
- perde acesso às áreas autenticadas;
- não recupera acesso utilizando código temporário antigo;
- não mantém sessão válida indefinidamente;
- não é apagado automaticamente;
- mantém histórico/auditoria necessários.

O Administrador não pode desativar usuários de outra organização.

Proteger situações em que um administrador tente remover o último
administrador necessário da organização.

Super Admin mantém capacidade de intervenção administrativa.
