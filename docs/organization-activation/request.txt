CORREÇÃO PÓS-HOMOLOGAÇÃO REAL — VIRELOQ
ATIVAÇÃO DE EMPRESAS, PRIMEIRO ADMINISTRADOR, PRIMEIRO ACESSO,
GESTÃO PELO SUPER ADMIN, AUDITORIA E CICLO DE VIDA

IMPORTANTE:

Esta solicitação é uma CORREÇÃO INCREMENTAL FUNCIONAL sobre a última
versão completa da VIRELOQ, já contendo a migration 026 e o novo modelo
de acesso empresarial.

A migration 026 já foi aplicada no ambiente real de homologação.

O novo acesso do Super Admin foi homologado com sucesso no Supabase real
após criação de uma identidade Auth limpa e execução do bootstrap oficial.

NÃO reconstruir a autenticação do zero.

NÃO retornar ao modelo de convite por e-mail.

NÃO alterar migrations 001–026 já existentes.

Se alguma mudança de schema for realmente indispensável, criar migration
027 incremental.

Não acessar nem modificar o Supabase real.

Não realizar deploy.

Não utilizar credenciais reais.

Não produzir vídeo.

O vídeo continua SUSPENSO.

==================================================
1. CONTEXTO DA HOMOLOGAÇÃO REAL
==================================================

Durante a homologação real da versão com enterprise access, o fluxo de
Super Admin funcionou.

Entretanto, foram encontrados problemas e lacunas na jornada de criação
e ativação de empresas.

O objetivo desta correção é resolver esses pontos SEM modificar os
princípios já aprovados:

LOGIN NORMAL:

Código da empresa
+
Username
+
Senha

PRIMEIRO ACESSO / REDEFINIÇÃO:

Código da empresa
+
Username
+
Código temporário
→ definição da senha definitiva.

O usuário empresarial é previamente PROVISIONADO.

Primeiro acesso NÃO cria uma segunda conta.

==================================================
2. CRIAÇÃO DE EMPRESA — DOIS MODOS
==================================================

O Super Admin deve poder criar uma empresa de DUAS maneiras:

A) Empresa + primeiro Administrador

ou

B) Empresa sem Administrador inicial.

O primeiro Administrador NÃO deve ser obrigatório para a existência da
organização.

==================================================
3. EMPRESA SEM ADMINISTRADOR
==================================================

Quando o Super Admin criar uma empresa sem Administrador:

- criar normalmente a organização;
- gerar seu código empresarial;
- preservar trial/plano conforme regras existentes;
- não criar usuário fictício;
- não criar Administrador fantasma;
- não criar membership artificial.

A empresa deve ficar claramente identificada como:

“Aguardando administrador”

ou equivalente.

Também deve ser apresentada como estando:

“Sob gestão da VIRELOQ”

enquanto não possuir Administrador empresarial.

==================================================
4. SUPER ADMIN PODE ABRIR EMPRESA SEM ADM
==================================================

Uma organização sem Administrador empresarial deve continuar acessível ao
Super Admin.

Na Administração VIRELOQ, o Super Admin deve poder:

- visualizar a empresa;
- abrir seu ambiente;
- configurar o que suas permissões globais já autorizarem;
- acompanhar seu estado;
- posteriormente definir o primeiro Administrador.

Não obrigar a criação de um ADM somente para o Super Admin conseguir
visualizar a empresa.

Não criar membership empresarial fictício para o Super Admin se o papel
global existente já autorizar essa operação.

Preservar RLS e autorização server-side.

==================================================
5. DEFINIR ADMINISTRADOR POSTERIORMENTE
==================================================

Empresa criada sem ADM deve possuir ação clara:

“Definir administrador”

ou equivalente.

Essa ação deve permitir informar:

Nome
Sobrenome
Username
E-mail obrigatório
Telefone opcional

Ao concluir, deve utilizar exatamente o mesmo mecanismo seguro de
provisionamento utilizado quando o ADM é criado junto com a empresa.

==================================================
6. SLUG / IDENTIFICADOR PÚBLICO AUTOMÁTICO
==================================================

Na criação da empresa, o campo do identificador público não deve exigir
que o Super Admin conheça manualmente o formato esperado.

Ao preencher:

Nome da empresa:
MS Auto Details

a interface deve sugerir automaticamente:

ms-auto-details

como identificador/slug público.

Mostrar visualmente a finalidade, por exemplo:

Endereço público:
 /empresa/ms-auto-details

O slug sugerido deve:

- ser normalizado;
- utilizar formato compatível com URL;
- remover/normalizar acentos quando necessário;
- converter espaços adequadamente;
- evitar caracteres inválidos;
- validar conflito;
- continuar editável pelo Super Admin antes da criação.

Se o nome for alterado ANTES da criação e o slug ainda não tiver sido
editado manualmente, atualizar a sugestão automaticamente.

Depois que o Super Admin editar manualmente o slug, não sobrescrever sua
edição automaticamente.

Não confundir SLUG PÚBLICO com CÓDIGO EMPRESARIAL.

==================================================
7. CÓDIGO DA EMPRESA
==================================================

Cada empresa deve possuir o código empresarial definido na arquitetura
da migration 026.

Exemplo conceitual:

MSA7K2

Esse código:

- é diferente do slug;
- identifica o tenant durante o login;
- não é uma senha;
- não deve ser escolhido manualmente pelo cliente;
- deve ser gerado pelo mecanismo seguro já implementado;
- deve possuir unicidade;
- deve ser exibido claramente ao Super Admin depois da criação.

Não substituir esse código pelo slug.

==================================================
8. CRIAÇÃO DE EMPRESA + PRIMEIRO ADM
==================================================

Quando o Super Admin escolher criar empresa JÁ COM Administrador inicial,
a operação precisa concluir toda a preparação necessária.

Fluxo esperado:

Super Admin
→ cria organização
→ código empresarial é gerado
→ identidade do ADM é provisionada
→ profile é criado/preparado
→ username é reservado
→ membership admin_empresa é criado
→ código temporário é gerado
→ conta fica aguardando primeiro acesso.

IMPORTANTE:

O usuário do ADM JÁ EXISTE antes do primeiro acesso.

Primeiro acesso NÃO cria outro auth.users.
Primeiro acesso NÃO cria outro profile.
Primeiro acesso NÃO cria outro membership.

Ele apenas ATIVA a identidade previamente provisionada.

==================================================
9. FALHA PARCIAL ENCONTRADA NA HOMOLOGAÇÃO
==================================================

Na homologação real foi observado o seguinte comportamento:

- o formulário de criação foi preenchido;
- a organização foi criada;
- ao final a interface informou que não foi possível concluir;
- a empresa permaneceu cadastrada;
- não ficou claro se o primeiro ADM havia sido completamente provisionado;
- o código temporário não foi apresentado ao Super Admin.

Corrigir essa experiência.

A operação não pode deixar o usuário sem saber o que aconteceu.

==================================================
10. OPERAÇÃO RETOMÁVEL / IDEMPOTENTE
==================================================

Se organização for criada, mas uma etapa posterior do provisionamento do
ADM falhar:

NÃO criar outra organização quando o Super Admin tentar novamente.

NÃO duplicar profile.
NÃO duplicar Auth user.
NÃO duplicar membership.
NÃO duplicar trial.
NÃO gerar estado inconsistente.

A interface deve identificar o estado real e oferecer algo como:

“Configuração incompleta”

“Continuar configuração”

ou ação equivalente.

Reutilizar a infraestrutura de retomada/idempotência já implementada na
026 quando aplicável.

==================================================
11. ERRO PRECISA SER ESPECÍFICO E ÚTIL
==================================================

Não finalizar esse fluxo apenas com:

“Não foi possível concluir.”

quando o backend possui informação segura suficiente para indicar a etapa
afetada.

Sem revelar detalhes sensíveis, distinguir situações como:

- organização criada, administrador pendente;
- username em conflito;
- e-mail administrativo inválido;
- provisionamento temporariamente indisponível;
- código temporário não gerado;
- operação já concluída;
- configuração incompleta recuperável.

Não expor detalhes internos de segurança.

==================================================
12. CÓDIGO TEMPORÁRIO DO PRIMEIRO ADM
==================================================

Ao provisionar o primeiro Administrador, gerar obrigatoriamente o código
temporário utilizando a infraestrutura segura já implementada.

Preservar as regras atuais:

- 48 horas por padrão;
- cinco tentativas por padrão;
- armazenamento somente do hash;
- uso único;
- novo código invalida o anterior;
- não registrar código em claro em logs;
- não permitir recuperação posterior do valor em claro.

==================================================
13. TELA DE SUCESSO DA ATIVAÇÃO
==================================================

Quando a empresa e seu primeiro ADM forem preparados com sucesso, mostrar
uma confirmação clara.

Exemplo conceitual:

EMPRESA ATIVADA

Empresa:
MS Auto Details

Código da empresa:
MSA7K2

Administrador:
João Silva

Usuário:
joao.silva

Código temporário:
8KPX-42MD

Válido até:
[data/hora]

[ Copiar instruções de acesso ]

[ Abrir empresa ]

Não hardcodar esses dados.

O código temporário em claro deve aparecer somente conforme a política
segura de entrega já definida.

==================================================
14. PRIMEIRO ACESSO NÃO É NOVO CADASTRO
==================================================

Este requisito é fundamental.

Quando o Administrador recebe:

Código da empresa
Username
Código temporário

e realiza o primeiro acesso, ele NÃO está criando uma conta nova.

A conta já foi criada/provisionada pelo Super Admin.

O fluxo deve reconhecer:

“Identidade existente aguardando ativação.”

Depois da validação do código temporário, apresentar:

Crie sua senha

Nova senha
Confirmar nova senha

[ Ativar meu acesso ]

Ao confirmar:

- definir a senha definitiva utilizando Supabase Auth;
- preservar o MESMO auth.users;
- preservar o MESMO profile;
- preservar o MESMO membership;
- preservar o MESMO username;
- preservar a MESMA organização;
- invalidar definitivamente o código temporário;
- marcar a conta como ativa;
- registrar auditoria;
- prosseguir para aceite legal quando aplicável;
- liberar acesso ao painel.

==================================================
15. LOGIN DEPOIS DA ATIVAÇÃO
==================================================

Depois do primeiro acesso, o código temporário nunca mais deve funcionar.

Login normal:

Código da empresa
+
Username
+
Senha criada pelo próprio usuário.

Preservar “Lembrar esta empresa” conforme implementação atual.

==================================================
16. ENVIO DAS INSTRUÇÕES POR E-MAIL
==================================================

Foi identificado um requisito omitido na revisão anterior.

Todo Administrador possui e-mail obrigatório.

Portanto, ao provisionar:
- primeiro Administrador;
- Administrador adicional;

a VIRELOQ deve tentar enviar automaticamente as instruções de primeiro
acesso ao e-mail cadastrado.

O e-mail deve conter:

- nome da empresa;
- código da empresa;
- username;
- código temporário;
- validade;
- link/botão para abrir a tela oficial da VIRELOQ;
- orientação de que a pessoa criará sua própria senha.

==================================================
17. E-MAIL NÃO VOLTA A SER A IDENTIDADE
==================================================

IMPORTANTE:

Esse envio NÃO reintroduz o antigo modelo de convite por e-mail.

O e-mail:
- não é o username;
- não substitui o código da empresa;
- não autentica sozinho;
- não cria a conta;
- não deve conter link que conceda acesso sem código temporário;
- não deve depender de magic link para provisionamento.

A conta já existe.

O e-mail é somente um CANAL DE ENTREGA das instruções.

==================================================
18. FALHA DE SMTP NÃO DESFAZ PROVISIONAMENTO
==================================================

Se o envio do e-mail falhar:

- NÃO apagar empresa;
- NÃO apagar ADM;
- NÃO apagar membership;
- NÃO gerar outro usuário;
- NÃO considerar toda a ativação perdida.

Mostrar ao Super Admin:

“Administrador criado. Não foi possível enviar as instruções por e-mail.”

e disponibilizar:

[ Copiar instruções ]

[ Reenviar instruções ]

O Super Admin poderá enviar pelo WhatsApp ou outro canal.

==================================================
19. REENVIAR INSTRUÇÕES
==================================================

Adicionar ação apropriada para Administradores aguardando ativação.

“Reenviar instruções”

Respeitar:
- rate limit;
- estado atual;
- validade;
- segurança.

Se for necessário gerar um NOVO código temporário, informar claramente
ao Super Admin que o código anterior será invalidado.

Nunca manter dois códigos válidos simultaneamente para a mesma geração de
acesso.

==================================================
20. FUNCIONÁRIOS
==================================================

Preservar o fluxo já implementado para funcionários.

Administrador empresarial:
→ cria usuário
→ identidade é provisionada
→ código temporário é gerado
→ funcionário ativa a MESMA identidade
→ cria sua própria senha.

E-mail continua opcional para usuários não administrativos.

Não tornar SMTP requisito para funcionário comum.

==================================================
21. AUDITORIA GLOBAL — EXCLUSIVA DO SUPER ADMIN
==================================================

A aba/área “Auditoria” da Administração VIRELOQ deve ser EXCLUSIVA de
usuários com papel global:

super_admin ativo.

Administradores empresariais NÃO devem visualizar essa opção.

Colaboradores NÃO devem visualizar.

Atendentes NÃO devem visualizar.

Nenhum usuário empresarial deve acessar a Auditoria global.

==================================================
22. NÃO BASTA ESCONDER O MENU
==================================================

Proteger Auditoria em todas as camadas necessárias:

- navegação;
- rota;
- RPC/API;
- RLS/policies;
- funções server-side.

Um admin_empresa digitando a URL diretamente NÃO pode obter os dados.

Uma chamada manual ao backend também NÃO pode retornar auditoria global.

Não confiar apenas no React/frontend.

==================================================
23. EVENTOS CONTINUAM SENDO REGISTRADOS
==================================================

Restringir leitura não significa parar de auditar.

Continuar registrando eventos relevantes, incluindo quando aplicável:

- empresa criada;
- empresa desativada;
- empresa reativada;
- tentativa/exclusão permitida;
- Administrador provisionado;
- usuário provisionado;
- ativação;
- redefinição;
- mudança de papel;
- aceite legal;
- ações administrativas relevantes.

O Super Admin continua podendo consultar a auditoria global.

==================================================
24. HISTÓRICO EMPRESARIAL É OUTRO CONCEITO
==================================================

Se existir ou futuramente existir histórico destinado ao ADM da empresa,
não chamá-lo nem tratá-lo como Auditoria global da VIRELOQ.

Ele deve ser:
- separado;
- limitado à própria organização;
- autorizado server-side.

Não ampliar escopo nesta correção se isso ainda não existir.

==================================================
25. CICLO DE VIDA DA EMPRESA
==================================================

O Super Admin precisa possuir ações distintas:

DESATIVAR EMPRESA

REATIVAR EMPRESA

EXCLUIR PERMANENTEMENTE

quando a exclusão for permitida.

Essas ações têm significados diferentes.

==================================================
26. DESATIVAR EMPRESA
==================================================

Desativação:

- NÃO apaga organização;
- NÃO apaga histórico;
- NÃO apaga trial;
- NÃO apaga billing;
- NÃO apaga auditoria;
- bloqueia operação/acesso conforme regras existentes;
- permite reativação posterior.

Utilizar os estados/infraestrutura existentes sempre que possível.

==================================================
27. REATIVAR EMPRESA
==================================================

Super Admin deve poder reativar empresa previamente desativada quando as
regras permitirem.

Reativar:
- não cria nova organização;
- não cria novo trial;
- não cria novos usuários;
- preserva histórico.

Registrar auditoria.

==================================================
28. EXCLUSÃO PERMANENTE
==================================================

Super Admin deve possuir autonomia para remover organizações criadas por
engano, duplicadas ou exclusivamente para teste, quando for seguro.

Exemplo real de homologação:

Uma empresa foi criada durante teste, a preparação do ADM falhou e a
organização permaneceu cadastrada.

O Super Admin precisa conseguir limpar esse registro quando ele não possui
histórico que obrigue preservação.

==================================================
29. EXCLUSÃO NÃO É DELETE CASCADE IRRESTRITO
==================================================

Não implementar botão que simplesmente execute DELETE CASCADE sobre
qualquer empresa.

Antes da exclusão permanente, verificar server-side:

- existência de operação relevante;
- clientes;
- solicitações;
- orçamentos;
- agenda;
- atendimentos;
- billing;
- trial;
- aceites legais;
- auditoria;
- outros registros que precisem ser preservados.

Empresas com histórico relevante devem preferencialmente ser
desativadas/encerradas conforme regras aplicáveis.

==================================================
30. CONFIRMAÇÃO FORTE DE EXCLUSÃO
==================================================

Quando exclusão permanente for permitida, exigir confirmação explícita.

Exemplo:

Excluir permanentemente MS Auto Details?

Esta ação não poderá ser desfeita.

Para confirmar, digite:

MS Auto Details

[ __________________ ]

[ Excluir permanentemente ]

Não depender apenas de confirm() do navegador.

==================================================
31. TRIAL NÃO PODE SER REINICIADO POR EXCLUSÃO
==================================================

Este requisito é obrigatório.

Excluir uma empresa NÃO pode apagar os registros mínimos necessários para
impedir abuso de trial.

Criar empresa
→ consumir trial
→ excluir empresa
→ criar novamente

NÃO pode resultar automaticamente em novo trial quando a elegibilidade
existente impedir isso.

Preservar:
- fingerprints;
- consumed keys;
- elegibilidade;
- evidências mínimas necessárias;
- política existente.

Não enfraquecer a proteção antifraude.

==================================================
32. EMPRESA RECÉM-CRIADA / CONFIGURAÇÃO INCOMPLETA
==================================================

Na Administração VIRELOQ, empresas sem ADM ou com provisionamento
incompleto devem mostrar estado claro.

Exemplos:

“Aguardando administrador”

“Configuração incompleta”

“Sob gestão da VIRELOQ”

Evitar mostrar simplesmente “Ativa” quando a jornada necessária ainda não
foi concluída.

Ações apropriadas:

[ Abrir empresa ]
[ Continuar configuração ]
[ Definir administrador ]
[ Desativar ]
[ Excluir empresa ]

Mostrar somente ações compatíveis com o estado real.

==================================================
37. CRIAÇÃO DA IDENTIDADE AUTH DO ADM
==================================================

Ao conceder acesso ao Administrador, a identidade Auth necessária deve
ser criada/provisionada automaticamente pelo backend da VIRELOQ.

O Super Admin NÃO deve precisar:

- entrar manualmente no Supabase;
- criar auth.users manualmente;
- definir senha definitiva;
- executar SQL;
- conhecer UUID;
- criar profile manualmente;
- criar membership manualmente.

Toda essa preparação deve fazer parte do provisionamento da VIRELOQ.

A senha definitiva será criada posteriormente pelo próprio ADM através
do primeiro acesso.

==================================================
38. SENHA TEMPORÁRIA NÃO É SENHA DEFINITIVA
==================================================

O código temporário NÃO deve se tornar a senha permanente.

Ele serve exclusivamente para comprovar que o usuário recebeu a
credencial de ativação previamente provisionada.

Depois de validado:

Código da empresa
+
Username
+
Código temporário

a interface deve abrir:

Nova senha
Confirmar nova senha

[ Ativar meu acesso ]

A senha definitiva deve respeitar a política de segurança configurada.

==================================================
39. PRIMEIRO LOGIN — EXPERIÊNCIA ESPERADA
==================================================

A experiência deve ser simples.

Na tela de acesso:

Código da empresa
Username
Senha ou código de primeiro acesso

ele for provisionado/ativado.

Preservar o estado pendente até isso acontecer.

44. TESTES — CRIAÇÃO DE EMPRESA
